# Головная Боль Админа

Macaroni Messenger сейчас отправляет текст.

Сейчас.

Это слово тут важнее, чем кажется.

Потому что Macaroni Messenger не столько доказывает, что можно сделать чат в git.

Это уже смешно, но ладно.

Он показывает штуку неприятнее:

```text
если у пользователя есть браузер,
JavaScript,
localStorage
и выход в интернет,
то у пользователя уже есть runtime для коммуникационного клиента
```

Не приложение.

Не installer.

Не Electron.

Не "платформа для коллаборации".

Просто HTML-файл.

Двойной клик.

Привет.

И вот здесь отдел безопасности обычно делает вид, что не моргнул.

## Это Не План Побега

Macaroni Messenger не задумывался как средство обхода корпоративных политик.

Не задумывался как бэкдор.

Не задумывался как инструкция "как вынести данные и испортить себе жизнь".

Это важная часть шутки.

Мы не принесли новый страшный инструмент.

Мы открыли браузер и увидели, что инструмент уже лежит там.

Браузер и так умеет:

- запускать JavaScript;
- хранить данные;
- читать файлы;
- отправлять запросы;
- работать с web API;
- показывать текст, картинки, аудио, видео и весь остальной цифровой суп.

Macaroni не добавляет новую физику.

Он просто убирает с неё корпоративную наклейку.

Если вы нарушитель, это не инструкция.

Если вы админ, это список мест, где привычная модель контроля делает неприятный хруст.

## Где Тут Смешно

Обычная корпоративная картина мира:

```text
есть разрешённые приложения
есть запрещённые приложения
есть installer
есть домен
есть binary
есть список того, что нельзя
```

Macaroni приносит другую картину:

```text
есть браузер
есть HTML
есть git-host API
есть пользователь
есть файлы
```

Запрещённое приложение не пришло.

Оно не установилось.

Оно не попросило права администратора.

Оно не появилось в списке программ.

Оно просто оказалось документом, который браузер умеет выполнять.

Вот здесь смешно.

Не потому что кто-то "обошёл защиту".

А потому что защита была построена вокруг формы приложения, а не вокруг движения данных.

## Что На Самом Деле Доказано

Macaroni Messenger не доказывает, что мы написали опасный механизм.

Он доказывает, что существующих browser primitives уже хватает, чтобы клиент был:

- одним HTML-файлом;
- открытым через `file://`;
- размещённым где угодно;
- сохранённым через Save As;
- отправленным по почте;
- положенным в wiki;
- прикреплённым к issue;
- скачанным из репозитория;
- запущенным двойным кликом;
- перенесённым на флешке;
- обёрнутым в WebView, если кому-то очень хочется, чтобы мессенджер весил 500 МБ.

С точки зрения пользователя это "просто страница".

С точки зрения браузера это приложение.

С точки зрения отдела безопасности это вопрос:

```text
как искать приложение,
если приложение не устанавливается?
```

Неприятный ответ:

```text
искать приложение поздно
```

Надо смотреть на данные, сеть, токены, browser policies и remote endpoints.

Да, это скучнее.

Да, это дороже.

Да, это взрослая работа.

Вот здесь тоже смешно, но уже не всем.

## Текст Сегодня, Байты Завтра

Macaroni Messenger сейчас пишет Protocol v1 text messages.

Это реализация, достаточная для proof of concept.

Точнее, proof of pasta.

Мы доказали не "можно отправить текст".

Мы доказали, что HTML-файл может быть транспортом.

Дальше инженер сам увидит, куда это может приехать: если транспорт есть, груз начинает задавать неудобные вопросы.

Браузер умеет держать bytes в `ArrayBuffer`, собирать `Blob`, кодировать base64, читать локальные файлы, кешировать данные, шифровать, хешировать и отправлять HTTP(S) requests.

То есть концептуально "сообщение" может быть не только текстом.

Оно может быть:

- текстом;
- ссылкой;
- base64 payload;
- набором chunks;
- git blob;
- LFS pointer;
- encrypted pasta;
- любой последовательностью байтов, которую plugin смог превратить в message.

Это не обещание сделать всё завтра.

Не потому что сложно.

Потому что нам лень.

Но сам факт неприятный: граница проходит не там, где хочется нарисовать её в политике безопасности.

Если WhatsApp Web может быть веб-приложением с медиа, то браузер уже умеет быть клиентом для медиа.

Остальное часто просто попытка спрятать природу приложения под проприетарной обёрткой.

Тот же browser runtime, только с логотипом, updater'ом и ощущением, что теперь всё серьёзно.

## Шифрование Добавляет Перцу

Macaroni уже умеет шифроваться через plugin.

Мы не называем это military-grade.

Мы не говорим "сертифицировано, проверено, можно спать".

Мы говорим честнее:

```text
в репозитории лежит encrypted pasta,
ключ живёт в HTML/localStorage,
если у вас есть файл - вы внутри,
если файла нет - приятного аппетита
```

И вот здесь смешно.

Потому что для администратора encrypted payload в разрешённом browser flow может быть хуже, чем plaintext в запрещённом приложении.

Plaintext хотя бы видно.

Encrypted pasta выглядит как мусор, ведёт себя как файл и едет туда же, куда разрешено ехать обычному git-трафику.

Мы не утверждаем, что это криптографический бункер.

Мы утверждаем, что это достаточно неприятный шкаф, чтобы в него начали заглядывать.

## Нельзя Просто Заблокировать "Мессенджер"

Заблокировать "Macaroni Messenger" можно.

Это несложно.

Можно даже написать policy.

Она будет выглядеть солидно.

Проблема в том, что форма остаётся:

```text
browser runtime + storage + remote file API = communication channel
```

И эта форма не обязана называться Macaroni.

Она может называться:

- `report.html`;
- `invoice.html`;
- `dashboard.html`;
- `new_year_card.html`;
- `final_final_really_final.html`;
- "ничего, это просто сохранённая страница".

Если контроль построен вокруг имени приложения, он проигрывает имени файла.

Если контроль построен вокруг одного домена, он проигрывает другому repository host.

Если контроль построен вокруг расширения файла, он проигрывает браузеру, который по работе и так открывает HTML.

Не драматично.

Просто факт.

Неприятный.

## Найти Файл Тоже Не План

Вопрос:

```text
как найти messenger.html?
```

Плохой вопрос.

Файл может называться не `messenger.html`.

Никто не мешает назвать его `котик.jpg`, `пёсик.txt`, засунуть в RARJPEG или ещё как-то неочевидно упаковать.

Это не делает файл магическим.

Это делает поиск по имени декоративным.

Правильный вопрос другой:

```text
какие данные могут покинуть управляемую среду
и через какие разрешённые каналы?
```

Macaroni просто делает этот вопрос смешно наглядным.

Неприятность не в том, что файл невозможно найти.

Неприятность в том, что найденный файл не отвечает на вопрос, почему он вообще смог работать.

## Плагины Делают Хуже

Macaroni держит core маленьким.

Сложные вещи уходят в plugins.

Для проекта это хорошо.

Для threat model - смешная пощёчина.

Plugin может быть:

- форматтером;
- encryptor'ом;
- import/export layer;
- attachment adapter;
- local redactor;
- media preprocessor;
- чем угодно, что можно написать на JavaScript.

Core остаётся одним HTML.

Plugin остаётся JavaScript.

Browser остаётся browser.

А отдел безопасности остаётся с вопросом:

```text
это всё ещё просто страница?
```

Да.

И нет.

Вот здесь смешно, потому что оба ответа правильные.

## Это Уже Было Возможно

Спокойно.

Macaroni не изобрёл утечку данных.

До Macaroni файл уже можно было:

- отправить по email;
- загрузить в облако;
- вынести на телефоне;
- скопировать на флешку;
- положить в pastebin;
- спрятать в архив;
- перепечатать руками, если человеку совсем скучно.

Macaroni не изобрёл браузер.

Macaroni не изобрёл git.

Macaroni не изобрёл способ делать больно отделу безопасности.

Он просто соединил:

```text
HTML
Git
JSON
```

И получил коммуникационный клиент.

Не новую физику.

Старую физику без галстука.

Ящик Пандоры уже стоял в браузере.

Macaroni просто открыл крышку и спросил:

```text
вы точно хотите строить security model
на предположении,
что HTML-файл является просто документом?
```

## Что Делать Админу

Не искать конкретно Macaroni.

Это красивая, но слабая стратегия.

Лучше задавать скучные вопросы:

- зачем пользователям доступ к внешним git-hosts;
- какие git-hosts действительно нужны для работы;
- какие token scopes допустимы;
- кто может создавать personal access tokens;
- как быстро tokens отзываются;
- можно ли писать в личные repositories с managed endpoints;
- проверяются ли outbound commits на чувствительные данные;
- проверяются ли attachments и archives;
- есть ли DLP на уровне содержимого;
- логируются ли API writes;
- кто смотрит на аномальный объём small file writes;
- есть ли политика для local HTML apps;
- что происходит с browser storage при увольнении сотрудника;
- что считается разрешённым collaboration tool.

Это не романтично.

Это не мем.

Это просто нормальная security работа.

И есть неиллюзорная вероятность, что люди, ответственные за эту работу, давно имитируют бурную деятельность.

Без крика.

Без обвинений.

Просто неприятное наблюдение.

Macaroni не заменяет эту работу.

Macaroni показывает, где её не было.

## Итог

Macaroni Messenger - головная боль отдела безопасности не потому, что он хитрый.

Он как раз тупой.

Неприлично тупой.

Один HTML.

Один browser runtime.

Один git repository.

Именно поэтому он неприятен.

Сложную систему можно записать в реестр, завернуть в MDM, заблокировать по bundle id и показать красивый отчёт.

Файл сложнее уважать.

Он слишком простой.

Macaroni показывает, что если у пользователя есть browser, JavaScript, local storage и network access, то приложение может быть не приложением.

Оно может быть файлом.

А вопрос "как запретить мессенджер" внезапно превращается в вопрос:

```text
как мы вообще управляем данными?
```

Вот здесь смешно.

Потому что это уже не про Macaroni.

Это про вас.
